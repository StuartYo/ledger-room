## What is compared

- **Ledger Room**: OCR + the model transcribe each document; deterministic code applies the six rules (UBN checksum, duplicates within a client and across clients, VAT Act Art. 19, client policy limits, filing period).
- **Pure model**: the same model, same photo, same OCR lines, with the six rules, the client's policy and the filing period written into the prompt. For duplicates it gets a running list of the documents it already reviewed, built from its own earlier answers. No code checks.
- **Oracle control**: the rule engine fed the ground-truth fields (no model). It must score 100%; it proves the answer key and the rules agree, and isolates reading errors.
- **Positive control**: a clean batch, then the same batch with one planted change per issue type, run through the full stack.

Held-out set: different seed, different clients, different layouts (family B: other fonts, column order, landscape receipts, stronger photo effects). Its answers were committed before any prompt or code tuning; tuning used the main set only. After the first evaluation, four fixes were made (one prompted by a held-out error, one by the positive control); the blind numbers from before them are kept below under "First blind run".

Bugs found by reading those errors and fixed afterwards (four):

- UBN roles: a 買方 label owns one number; a line OCR reads as '方：12345678' (the 賣 dropped) is the seller's. (held-out)
- Totals: skip the e-invoice random code when OCR prints it in mixed characters (随機码), and prefer the number on the 總計 / 合計 row over the largest number on the page. (positive control)
- Seller name: take the stamp's name line when the stamp is rotated. (seen in the web app)
- Expense category: seller names now match only multi-character terms (餐廳, 咖啡, 商旅...). Fix 3 exposed this on the main set, where OCR read a garage stamp 保養廠 as 保餐廠. (main)

## Totals picked by code

**Totals picked by code** (eval/totals_eval.py). Code collects the printed evidence for the total (the 總計 / 合計 / 應付 row, the e-invoice random-code line, a net + 5% tax = total triple, the amount in Chinese numerals, the subtotal) and ignores numbers on cash, change, balance, card, deposit, points and reference lines. The model's own total, and its answer to a follow-up question asked only when the evidence is thin, count as one vote each, and only if that number is printed on the page. A total needs two agreeing sources and no tie; otherwise it is marked unconfirmed and the document goes to a person (READ_REVIEW). "Before" is the previous code on the same model replies.

The six rules score the same with or without the vision model on both synthetic sets, because they run on OCR digits and code. The model matters for the amounts: its reading is the second vote that lets code confirm a total, so without it more key fields stay wrong and more documents go to a person (held-out: 10% (32/319) against 0% (0/319) wrong, 31 documents held against 0; main: 1% (4/345) against 0% (0/345), 5 held against 0). On the real photos the 2B reads dates 9/10 against 7/10 and totals 9/9 against 6/9, and pairs the meal detail with its payment slip (1/1 against 0/1; the pairing needs the date). The 9B row was measured with code c445b35, before totals were picked by code, so its reading error rate is not comparable with the rows above it. The OCR-only parser was written for this comparison against the synthetic label words and changed once after its first held-out run (folding simplified and traditional characters in the 銷售額 / 稅額 labels), so its held-out numbers are not blind.

## Limits

- Synthetic documents only; real phone photos, handwriting and faded thermal paper will be harder.
- The laptop timing uses the Intel UHD iGPU; Arc Pro B70 timings are not measured yet.
- The planted issues were designed by the author; the held-out set changes seed, clients and layouts but not the issue definitions.
- Held-out set 2 was also designed by the author, after the total-reading weakness was known; its clean synthetic print overstates real-photo accuracy.
